最終更新: 2026-08-08

## 0. このリポジトリが作るもの

| 出力 | 内容 |
|---|---|
| `out/audio/*.wav` | 24分の完全ループ音源（44.1kHz / 24bit / stereo） |
| `out/video/*.mp4` | **2時間24分**のアップロード用本編（1080p / AAC 256kbps） |
| `out/visual/*.mp4` | 20秒のループ映像（本編はこれを繰り返している） |
| `out/thumbnail/*.png` | サムネイル 1280×720 |
| `out/metadata/*.json` | タイトル・説明文・タグ（そのまま貼れる） |
| `out/preview/*.mp3` | 90秒の試聴用抜粋 |
| `out/report.json` | 検証結果（長さ / LUFS / トゥルーピーク / 継ぎ目） |

**外部素材はゼロです。** 音源も映像も、すべて numpy による手続き生成です。
サンプルパックもストック映像もフォント以外の外部アセットも使っていません。

## 1. 音の仕様

### 1-1. マスタリング

| 項目 | 値 | 根拠 |
|---|---|---|
| 統合ラウドネス | **−14 LUFS** | YouTube の正規化目標に一致させる |
| トゥルーピーク | **−1.0 dBTP 以下** | YouTube 推奨。エンコード時の歪みを防ぐ |
| サンプルレート | 制作 44.1kHz → 出力 48kHz | YouTube は 48kHz を推奨 |
| ビット深度 | 中間ファイルは 24bit | 静かな睡眠音源で量子化ノイズを乗せないため |
| 音声コーデック | AAC-LC 256kbps | YouTube 側で再エンコードされる前提の余裕を持たせた値 |

**なぜ −14 LUFS ちょうどなのか**

YouTube のラウドネス正規化は **「大きい音は下げるが、小さい音は上げない」** 一方向です。
つまり −18 LUFS で作っても音量は上がらず、そのまま小さいまま再生されます。

これが睡眠用BGMでは致命的になります。広告は −14 に正規化されて流れるため、
**BGMだけが小さく、広告だけが爆音**という状態になり、寝入りばなに叩き起こされます。
だから −14 に合わせるのが正解です。

### 1-3. 音源の構成レイヤー

```
  ┌─ メロディ         … 休符を多めに、コードトーンに着地
  ├─ コード伴奏       … ルートレスボイシング（ジャズ）/ クローズド（ポップ）
  ├─ ベース           … ルート / ポンプ / ウォーキング / ボサ
  ├─ ドラム・打楽器   … lofi / ブラシ / ボサ
  ├─ パッド           … コード間をクロスフェードで繋ぐ
  └─ ドローン         … 全長を通した持続音（睡眠・瞑想のみ）
        ↓
     リバーブ（合成IR・3バンド減衰）
        ↓
     ＋ 環境音ベッド（雨・焚き火・波・カフェ・部屋鳴り）
        ↓
     マスタリング（ティルトEQ → ローパス → サチュレーション）
        ↓
     −14 LUFS 正規化 → リミッタ（−1 dBTP）
```

## 2. 「2時間ループしても継ぎ目が出ない」仕組み

ここが本プロジェクトの技術的な核です。ふつうに作ると必ず継ぎ目にプチッというノイズが出ます。
それを消すために4つの対策を入れています。

### 2-1. ループ長を「秒」で固定し、BPMを逆算する

BPM を先に決めると、1周のサンプル数に端数が出ます。端数があると ffmpeg で
繰り返したときに位置がずれ、継ぎ目が生まれます。

そこで **ループ長 1440 秒（= 63,504,000 サンプル、ちょうど整数）を先に固定**し、
小節数から BPM を逆算しています。BPM が 78.00 か 77.84 かは誰にも聞き分けられません。

```python
bar_sec = 60.0 / target_bpm * 4
bars    = round(seconds / bar_sec)     # 小節数を整数に丸める
# → 実効BPM = 60 * 4 * bars / seconds
```

### 2-2. 残響を先頭へ折り返す（fold_tail）

ループ末尾で鳴っている音の残響は、本来「次の周回の頭」で鳴り続けるはずのものです。
そこで**ループ長より長く合成しておき、はみ出した尻尾を先頭へ巡回加算**します。

```python
out = x[:loop_len].copy()
tail = x[loop_len:]
while 残りがある:
    out[:len(chunk)] += chunk     # 尻尾を先頭へ巻き戻して足す
```

これで末尾→先頭の接続が数学的に完全に連続になります。
そのため各トラックには、**最長のサンプル + リバーブ長 + パッドのリリース**を
すべて収められるだけの余白（12〜38秒）を確保しています。

### 2-3. 環境音は「周期信号」として生成する

雨や波のノイズは、FFT領域で長さ n の周期信号として直接作っています（`looped_noise`）。
フィルタも**巡回畳み込み版**を使うので、端が痩せません。

- ノイズ床 … 短い巡回タイルを敷き詰める（フィルタ済みノイズには際立った過渡音がないため、タイル周期は知覚されない）
- 雨粒・薪のはぜる音 … **全長にわたってばら撒く**（ここに反復が出ると一発でバレる）
- ゆっくりした変調 … すべて**整数周期の LFO**

### 2-4. 持続音の周波数をスナップする

ドローンのように減衰しない音は、周波数がループ長で整数回振動しないと位相が飛びます。
そこで各部分音の周波数を「ループ長でちょうど整数周期になる値」へ丸めています。
ずれは 1/1440 ≒ 0.0007 Hz なので聴感上は完全に同一です。

### 2-5. マスタリングも巡回で適用する

EQ もリミッタもワウフラッターも、内部で前後のサンプルを参照します。
素直にかけると、せっかく消した継ぎ目が復活します。

そこで**信号の前後を巻き付けてから処理し、中央だけを取り出す**方式にしています
（`dsp.circular_process`）。

### 2-6. 検証方法

`out/report.json` に2つの指標を出しています。

| 指標 | 意味 | 合格ライン |
|---|---|---|
| `loop_seam_db` | 継ぎ目の段差 ÷ 曲中の通常の隣接サンプル差分（99.9%点） | **0 dB 以下**なら、曲中で普通に起きている変化より小さい＝知覚されない |
| `seam_dbfs` | 継ぎ目の段差の絶対量 | −40 dBFS 以下が目安 |

## 3. 映像の仕様

| 項目 | 値 |
|---|---|
| 解像度 | 1920×1080 |
| フレームレート | 15 fps |
| ループ長 | 20 秒（＝300フレーム） |
| コーデック | H.264 High / yuv420p |
| GOP | 10秒固定・シーンチェンジ検出オフ |

### なぜ 20 秒ループなのか

2時間24分ぶん（約13万フレーム）を描画するのは無駄です。
20秒の完全ループを作り、**ffmpeg の `-stream_loop` + `-c copy` で複製**しています。
再エンコードが発生しないので、本編の書き出しは数秒で終わります。

コピー連結が破綻しないよう、ループ映像は
**「先頭が必ず IDR フレーム」「シーンチェンジ検出オフ」「GOP長固定」**で作っています。

### 完全ループにするための制約

アニメーションはすべて位相 `t01 ∈ [0,1)` の周期関数で駆動しています。
状態を持つシミュレーション（炎の物理計算など）はループできないので使いません。

- 波・炎・湯気・オーロラ … 正弦波の重ね合わせによる周期ノイズ場
- 雨粒・火の粉・埃 … 位置は `(y0 + speed × t01) % 1`。**speed は整数**（非整数だと継ぎ目で粒子がワープする）
- 明滅 … `sin(2π × 整数 × t01)`

### 低ビットレートでも破綻させない工夫

グラデーションは低ビットレートでバンディング（縞）が出ます。
対策として **「動かない微細ノイズ」** を最初から乗せています。
静止ノイズなら最初の I フレームに一度入るだけで、P フレームは太りません。

また、毎フレーム計算する光の場やノイズ場は 1/3 解像度で計算して拡大しています。
柔らかい光には輪郭がないので、見た目は変わらず 9 倍速くなります。

## 4. 使い方

### セットアップ

```bash
pip install -r requirements.txt
```

必要なのは `numpy`, `pillow`, `imageio-ffmpeg` の3つだけです。
`imageio-ffmpeg` には静的ビルドの ffmpeg が同梱されるので、別途インストールは不要です。

### 実行

```bash
# 全10本を 2時間24分の動画として書き出す（数時間かかります）
python3 render_bgm.py

# 音源とメタデータだけ（映像をスキップ）
python3 render_bgm.py --no-video

# 特定のトラックだけ
python3 render_bgm.py --tracks 04_cozy_coffee_jazz 05_bossa_nova_cafe

# 動作確認（1分ループ × 3周 = 3分の動画）
python3 render_bgm.py --seconds 60 --repeats 3

# 8時間版を作る（同じ24分音源を20周）
python3 render_bgm.py --repeats 20
```

### 別バージョンを作る

**同じジャンルで違う曲**が欲しいときは `bgm_studio/tracks.py` の `seed` を変えるだけです。
コード進行・メロディ・ドラムパターン・環境音がすべて別物になります。

```python
TrackSpec(slug="01b_lofi_rainy_study", ..., seed=1012)   # 1011 → 1012
```

> ⚠️ ただし **同じ音源を使い回して複数本アップするのは絶対にNG**です（§01 のポリシー参照）。
> seed を変えて別の曲として生成してください。

## 5. 処理時間とディスクの目安

4コアCPU・メモリ16GB の環境での実測に基づく目安です。

| 工程 | 1トラックあたり |
|---|---|
| 音源合成（24分） | 5〜10分 |
| 映像ループ描画（300フレーム） | 1〜2.5分 |
| AAC化（2時間24分） | 2〜4分 |
| 多重化（コピーのみ） | 数秒 |
| **合計** | **10〜17分** |

10本で **2〜3時間**、ディスクは **10〜12GB** 程度必要です。

## 6. モジュール構成

```
bgm_studio/
  dsp.py          信号処理の土台（FIR / 畳み込みリバーブ / ラウドネス / リミッタ）
  theory.py       スケール・コード・進行・構成（和声がぶつからないようにする層）
  instruments.py  手続き生成のサンプルバンク（ピアノ / ローズ / ボウル / ドラム …）
  nature.py       環境音（雨 / 焚き火 / 波 / 風 / カフェ / 夜 / ブラウンノイズ）
  arrange.py      シーケンサ（誰がいつ何を弾くか。人間らしい揺れもここ）
  tracks.py       10本のトラック定義とマスタリング設定
  visuals.py      ループ映像のシーン生成
  video.py        WAV / MP4 書き出しと ffmpeg 合成
render_bgm.py     CLI
```

### 速度のための設計

音符を1つずつ合成すると2時間ぶんは到底終わりません。
そこで **「音程 × ベロシティ層 × 音色バリエーション」を一度だけ合成してキャッシュ**し、
シーケンサはキャッシュ済みの配列を加算するだけにしています（実質サンプラー）。

同様に、サンプル単位の Python ループは一切書いていません。
IIR フィルタが必要な場面は FFT 畳み込みかブロック再帰で代替しています。
