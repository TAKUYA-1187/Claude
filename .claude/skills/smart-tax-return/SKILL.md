# スマート確定申告 四半期提出ワークフロー

> **名称について**
> 運用上の正式名称は「スマート確定申告」。会話や過去資料では「スマカク」と略されることがあり、
> どちらも同じサービスを指す。ただし **OneDrive / Google Drive 上の実フォルダ名は
> `確定申告　スマカク` のまま**なので、パスは読み替えずにそのまま使うこと。

## このスキルが解決すること

確定申告代行サービス「スマート確定申告」には四半期ごとに大量の資料を提出する必要がある。
カードは17種類、PayPayは16口座、加えて売上・レシート・ポイント履歴。
提出先はGoogle Driveの入れ子になったカテゴリ別フォルダで、どこに何を入れるかは決まっている。

手作業でやると必ず取りこぼす。実際、過去の四半期では「フォルダは作ったが中身が空」「特定の月だけ抜けている」
「同じファイルを2つの四半期に入れてしまった」といった漏れが複数発生している。

このスキルの目的は、**取りこぼしを構造的に防ぐこと**。
そのために「集めて終わり」ではなく、必ず最後に前四半期と突き合わせる監査フェーズを置く。

## 全体の流れ

```
Phase 1: 棚卸し     今回の対象期間を確定し、既にあるもの／ないものを把握する
Phase 2: 収集       各サイトから明細をDLし、OneDriveの提出資料フォルダに集める
Phase 3: 振り分け   Google Driveのカテゴリ別フォルダへアップロードする
Phase 4: 監査       前四半期と突き合わせ、不足・重複・不整合を報告する
Phase 5: 指摘対応   提出後に会計士から届いた指摘に対応し、連絡文を返す
```

Phase 4 を省略しないこと。ここで見つかる漏れが一番多い。
逆に、ユーザーが「不足しているものを教えて」とだけ言った場合は Phase 1 と 4 だけを実行すればよい。
会計士からの指摘メールを渡された場合は Phase 5 だけでよい。

---

## Phase 1: 棚卸し

### 対象期間の確定

Driveの年度フォルダ配下は四半期で分かれている。

| フォルダ名 | 対象期間 | 期限 |
|---|---|---|
| `.01-03月分(4月末日まで期限)` | 1〜3月 | 4月末 |
| `.04-06月分(7月末まで期限)` | 4〜6月 | 7月末 |
| `.07-12月分(1月10日まで厳守)` | 7〜12月 | 翌1月10日 |

ユーザーが「4-6月分」と言えば `.04-06月分`、「今回の分」と言われたら今日の日付から判断する。
迷ったら聞く。期間を取り違えると全部やり直しになるので、ここは推測しない。

### チェックリストを読む

OneDriveの提出資料フォルダに、スマート確定申告から来たチェックリストが置かれていることがある。

```
確定申告　スマカク/2026_領収書/YYYYMM提出資料/【N-M月分】ダウンロード チェックリスト.md
```

これが**その回の正式な要求仕様**。カード一覧・必要な月・特記事項（AMEXは月次1ファイルでよい、等）が書いてある。
あれば必ず先に読む。無ければ前四半期の提出実績を仕様とみなす。

### 前回の作業記録を読む

このリポジトリの `smart_tax_return/records/` に、四半期ごとの作業記録が残してある。
**前回分を必ず先に読む。** 「前四半期で何を出したか」「未解決のまま持ち越した件は何か」
「どういう判断をしたか（請求月ベースのカード、重複と判定した明細など）」がまとまっていて、
Phase 1 の在庫確認と Phase 4 の監査がそのぶん短くなる。

今回の作業が終わったら、同じ形式で新しい記録を書き足すこと。次回の自分への申し送りになる。

### ローカルの在庫を確認

```bash
ls -la "/Users/<ユーザー名>/Library/CloudStorage/OneDrive-個人用/OneDrive/確定申告　スマカク/2026_領収書/YYYYMM提出資料/"
```

既にDL済みのファイルがあれば、そのぶんPhase 2をスキップできる。
ファイル名から「どのカードの何月分か」を読み取って対応表を作っておくと、Phase 3が一気に楽になる。

---

## Phase 2: 収集

取得元サイトごとの手順・ログイン事情・つまずきポイントは `references/source-sites.md` にまとめてある。
これから明細をDLするなら**先にそれを読むこと**。サイトによって罠が違う。

収集時の共通方針:

- **保存先は OneDrive の提出資料フォルダ**。Drive に直接入れず、いったんここに集める。
  こうしておくと「何が揃っていて何が無いか」がローカルで `ls` 一発で分かる。
- **ファイル名は変えない**。チェックリストにも「ダウンロードしたままの名前でOK」と明記されている。
  ただし後からどのカードか判別できない名前（`detail202604.csv` など）の場合は、
  カード名を足しておくと Phase 3 の振り分けで迷わない。
- **形式は Numbers でも CSV でも PDF でもよい**。スマート確定申告側で変換してくれる。
- **CSVエクスポート機能が無いサイト**（楽天ポイント、メルカリ等）は、ページを辿って
  テキストを抽出しCSVを組み立てる。手順は `references/source-sites.md` の該当節にある。

### ログインでブロックされたら

三井住友（Vpass）やJCBはbot検知でブロックされることがある。
その場合、無理に突破しようとせず**ユーザーに手動DLを依頼する**。
何のサイトの何月分が必要かを具体的に伝えれば、ユーザー側は数分で終わる。
突破を試みてアカウントをロックさせる方がはるかに高くつく。

---

## Phase 3: 振り分け（Driveへのアップロード）

### カテゴリ構造

四半期フォルダ直下は12のカテゴリに分かれている。全体像と、どのファイルがどこに行くかは
`references/drive-structure.md` を参照。02.クレカは中がさらにカード別サブフォルダに分かれていて、
ここが一番間違えやすい。

### アップロード前に必ず中身を見る

**上書きではなく追加**なので、既にファイルがあるフォルダに同じものを入れると重複する。
過去に実際、既に埋まっているフォルダに気づかず二重投入しかけた。

各フォルダにアップロードする前に、一度中身を列挙して
「本当に空か」「既に何月分が入っているか」を確認してから投入すること。
列挙の手順は `references/browser-techniques.md` にある。

### アップロード手順

ブラウザ操作の具体的な手順（新規→ファイルのアップロード→隠しinputにfile_upload）と、
よくある失敗（メニュークリックがホームに飛ぶ、行のダブルクリックが隣の行に当たる）の回避策は
`references/browser-techniques.md` にまとめてある。**Driveを操作する前に読むこと**。

要点だけ先に:
- フォルダへは**行をダブルクリックせず、フォルダIDのURLに直接navigateする**。行クリックは頻繁に隣に外れる。
- 1回の `file_upload` は合計10MB未満。超えるなら分割する。
- アップロード後はトーストの緑チェックを見て、件数が合っているか確認する。

## Phase 4: 監査（最重要）

前四半期のフォルダと今四半期のフォルダを全階層で突き合わせ、差分を報告する。

### 手順

1. 両四半期の全フォルダを列挙して JSON に落とす
   （`references/browser-techniques.md` の棚卸しスニペット + `scripts/drive_inventory.js`）
2. `scripts/compare_quarters.py` に2つのJSONを渡して差分を出す
3. 出力を読んで、機械的に拾えない項目（後述）を人間の目で補う

```bash
python3 scripts/compare_quarters.py prev.json curr.json
```

### 何を探すか

`compare_quarters.py` が自動で拾うもの:

| 種別 | 内容 |
|---|---|
| 空フォルダ | 前四半期には中身があったのに今回は空 |
| 消えたフォルダ | 前四半期にあったカード別フォルダが今回無い |
| 月次の抜け | ファイル名から月を抽出し、対象3ヶ月のうち欠けている月を検出 |
| 期間跨ぎ重複 | 同名ファイルが前四半期と今四半期の両方にある |
| フォルダ内重複 | 同一口座・同一月と思われるファイルが複数ある |

スクリプトでは拾えないので**必ず目視で確認するもの**:

- **口座番号・カード番号の変化** — ファイル名末尾の4桁が前四半期と違う場合（`enavi202603(旧4桁).csv` → `enavi202605(新4桁).csv`）、
  カード更新か別カードか判断できない。見つけたらユーザーに確認を促す。
- **請求月ベースか利用月ベースか** — 楽天カードの `enavi202605.csv` は「5月請求＝4月利用分」。
  ファイル名の月と対象月が1ヶ月ずれるカードがある。単純な月マッチングでは誤判定するので、
  該当カードは `references/drive-structure.md` の注記を見ること。
- **構造の違い** — 前四半期はサブフォルダ分け、今回は直置き、のような差。
  中身が揃っていれば実害は薄いが、報告はする。

### 報告フォーマット

監査結果は、ユーザーが**そのまま作業に移せる形**で出す。
「全部を平等に並べる」のではなく、緊急度で分ける。これが実際に一番役に立つ。

```markdown
## 🔴 至急対応が必要（空のまま）
（フォルダ名と、前四半期には何が入っていたかを添えた表）

## 🟡 月次の抜け
（カード名 / 今ある月 / 足りない月 の表）

## ⚠️ 要確認（重複・不整合）
（番号付きリスト。なぜ問題なのか一言添える）

## ✅ 揃っているもの
（列挙のみ。詳細は不要）
```

最後に「まずどれから着手しますか」と一言添えて、次の行動につなげる。

## Phase 5: 会計士からの指摘対応

提出後、スマート確定申告から箇条書きの指摘メールが届く。典型的には
「連携を解除して」「この資料を出して」「重複しているようです」の3種類。

### まず「どの四半期への指摘か」を特定する

**これを取り違えると、対応そのものが空振りする。**
会計士は複数の四半期を並行してチェックしているので、直近に提出した四半期への指摘とは限らない。

実際に起きた例: 4-6月分の提出直後に届いた指摘を4-6月分への指摘として対応したが、
後から「先日ご依頼した内容は1月-3月分の提出資料修正依頼です」と連絡が来た。
結果、1-3月分への追加提出が数ヶ月ぶら下がったままになった。

- メール／チャットに四半期の明示が無ければ、**推測せず聞く**
- 提出先フォルダ名が書かれていればそれが答え（`01-03月分(4月末日まで期限)` など）
- **期限が過ぎた四半期のフォルダにも追加提出する**ことがある。「もう締まっているはず」で止めない
- 様式変更（例: Amazon売上がCSVのみ → CSV+PDF）は、**過去の四半期に遡って適用を求められる**

### 進め方

指摘は番号ごとに独立しているように見えて、**片方が済んでいるともう片方の前提が変わる**ことがある。
まず全項目を読んで、確認だけで済むもの・実作業が要るもの・ユーザーにしか答えられないものに仕分ける。

そのうえで、**必ず「実際の状態」を見てから答える**。
過去に「解除作業中」とチェックリストに書かれていた項目が、確認したら既に完了していた例がある。
逆に「対応済み」と書かれていたのに実物が無かった例もある。記録ではなく現物を見る。

### 指摘の3類型と対応

**(a) 連携解除の依頼**

MFのデータ連携一覧を開いて、対象サービスが本当に残っているか確認する。
手順と判断基準は `references/mf-integrations.md`。

「銀行やクレジット連携でも利用履歴が判断できるようでしたら解除を」のように
**条件付き**で言われることがある。その場合は、その買い物がどのカードで決済されているか、
そのカードがMF連携されているかまで確認してから答える。
（例：楽天市場は楽天カード決済／Yahoo!ショッピングはPayPayカード決済。いずれも連携済みなので解除して問題ない）

**(b) 資料提出の依頼**

Phase 2〜3 と同じ要領。既に出しているつもりでも、フォルダを開いて実物を数える。

**(c) 重複の指摘**

ファイル名だけで判断しない。**中身で確かめる**。
`scripts/check_duplicates.py` が、同一内容・同一取引番号・同一口座の表記ゆれを検出する。

このワークフローで実際に起きた重複は3パターン:

| パターン | 例 | 対処 |
|---|---|---|
| 同じ資料をCSVとNumbersの両形式で提出 | `PAYPAY9999_....csv` と `....numbers` | Numbers版を不要データへ |
| 同じファイルの「のコピー」 | `....csvのコピー.csv` | コピー側を不要データへ |
| 同じ明細を別名で2回DL | ANA PASMO と JCB（本文完全一致） | 片方を不要データへ |

**紛らわしいが重複ではないもの**も必ず確認する。下4桁が同じでも別口座のことがある
（`PAYPAY9999`＝TAKUYA559999 と `PAYPAY079999`＝TAKUYA91079999 は別物だった。数字は例）。
提出状況報告シートの口座一覧と突き合わせれば判別できる。

### 重複ファイルは削除せず「不要データ」へ移す

各四半期フォルダに `不要データ[使用しないフォルダ 提出対象でない資料はこちらへ]` がある。
会計士側が用意した退避先なので、削除ではなくここへ移す。取り消しが利く。

移動の具体手順とハマりどころは `references/browser-techniques.md` の「ファイルを移動する」を読むこと。
**Driveの複数選択は自動操作では効かない**ので1件ずつになる。件数が多いときは、
所要時間を伝えたうえで手動を選んでもらうほうが早いことがある。

### 連絡文を書く

`references/accountant-feedback.md` にテンプレートがある。要点:

- **指摘の番号と見出しをそのまま使う**。会計士が照合しやすい
- 「対応済み」で終わらせず、**何を確認してそう言えるのか**を1行添える
  （悪い例：「解除済みです」／良い例：「解除済みです。現在の連携は銀行5件・カード11件の計16件のみです」）
- ついでに直した点があれば「その他、あわせて修正した点」として列挙する
- **確認できなかったことは書かない**。ユーザーにしか分からないこと
  （メルペイを使ったか、レシートが手元にあるか等）は推測で埋めず、必ず本人に聞く

最後の点が一番重要。事実でないことを会計士に報告すると、後で辻褄が合わなくなる。

---

## やってはいけないこと

- **ファイルやフォルダを削除しない**。重複を見つけても消さず、報告して判断を仰ぐ。
  提出済み資料の削除は取り返しがつかない。
- **不足を勝手に埋めない**。「たぶんこれだろう」で別の月のファイルを入れると、
  会計処理そのものが狂う。無いものは無いと報告する。
- **推測でチェックを付けない**。「対応済み」と書かれていても、実際にフォルダを見て確認する。
  チェックリストの記載と実態がずれていた例が既にある。
- **確認していないことを会計士への連絡文に書かない**。「ファイルが無い」は
  「取引が無かった」の証拠にならない。利用の有無はユーザー本人に聞く。
- **Driveの「アクセス権限をリクエスト」を押さない**。フォルダ所有者（会計士）に
  不要な承認依頼が飛ぶ。権限エラーが出たら `u/N` を変えてアカウントを切り替える。
- **連携解除を勝手に実行しない**。会計士のメールを転送されただけでは合意ではない。
  ユーザー本人の指示を待つ。
