# Drive / OneDrive の構造とファイルの行き先

## 保管場所は2つある

| 役割 | パス |
|---|---|
| 収集用ステージング（ローカル） | `/Users/<ユーザー名>/Library/CloudStorage/OneDrive-個人用/OneDrive/確定申告　スマカク/2026_領収書/YYYYMM提出資料/` |
| 提出先（Google Drive・スマート確定申告と共有） | 共有アイテム → `<顧客番号>-<氏名>様` → `2026（Aグループ）` → 四半期フォルダ |

bash から OneDrive を触るときのマウントパスは `/sessions/<session>/mnt/確定申告　スマカク/...`。
`file_upload` に渡すパスは macOS 側の絶対パス（`/Users/<ユーザー名>/...`）である点に注意。ここは混同しやすい。

Drive は複数アカウントでログインしていることがある。スマート確定申告の共有は `u/3`（URLの `/drive/u/3/`）。
Drive の MCP コネクタは別アカウントに繋がっていて**このフォルダが見えない**ので、ブラウザ経由で操作する。

## 四半期フォルダ

| フォルダ名 | 対象 | 期限 |
|---|---|---|
| `.01-03月分(4月末日まで期限)` | 1〜3月 | 4月末 |
| `.04-06月分(7月末まで期限)` | 4〜6月 | 7月末 |
| `.07-12月分(1月10日まで厳守)` | 7〜12月 | 翌1月10日 |

同階層に `提出完了連絡後_追加資料` と `.資料提出シート2026_<氏名>様`（スプレッドシート）がある。
提出シートはスマート確定申告側が状況を記入するもので、こちらの認識と食い違うことがある。実フォルダの中身を正とする。

### 06 と 07 の中の分類

- 07: 「経費」「仕入」「自己」「資金移動」でフォルダ分け
- 共通: **月ごとにフォルダを分けないこと**

### 10.売上[Amazonセラー] の様式変更

2026年4-6月分から、月ごとに **CSV（月別トランザクションレポート）と PDF（期間別概要レポート）の両方**が
必要になった（会計士からの指摘）。1-3月分はCSVのみだったので、前四半期と比較すると
「PDFが増えている」形になるが、これは不足ではなく改善。

取得元: Amazon セラーセントラル → レポート → ペイメント → 月別トランザクション

## 02.クレカ のカード別サブフォルダ

サブフォルダ名は**カード名 + 名義人**。名義は TAKUYA / KAORI / MICHIKA の3名。

チェックリストに載っている正式な13枚:

| カード | 名義 | 取得元 |
|---|---|---|
| 楽天カード | TAKUYA | 楽天e-NAVI → 明細照会 → CSV |
| 三井住友Visa Infinite | TAKUYA | Vpass → ご利用明細 → CSV |
| Oliveゴールド | TAKUYA | Vpass（Olive）→ ご利用明細 → CSV |
| JCBカード | TAKUYA / KAORI | MyJCB → ご利用明細照会 → CSV |
| AMEX | TAKUYA | アメックス会員サイト |
| ANA AMEX | TAKUYA / KAORI | 同上 |
| MARRIOTT AMEX | TAKUYA / KAORI | 同上 |
| AMAZONマスター | TAKUYA / KAORI 両方を1フォルダに | 三井住友カード会員サイト |
| PayPayカード | TAKUYA / KAORI / MICHIKA | PayPayカード会員メニュー |

2026年4-6月分で追加された、チェックリストには無いフォルダ:

- `ANA PASMO TAKUYA` / `ANA PASMO KAORI`
- `三井住友ゴールドNL TAKUYA`

これらは正式リストに無いため、**提出が必要かどうかユーザーに確認する**。
フォルダだけ作って空のまま放置すると、監査で毎回「空」として挙がり続けてノイズになる。

### 命名の癖と注意点

- サブフォルダ名の先頭に**半角スペースが入っているもの**がある（` JCBカード TAKUYA`、` PAYPAYカード KAORI` など）。
  文字列一致で探すときは trim すること。
- 指示ファイルには「MF連携済みクレカはフォルダ名に『MF連携済み』と記入してください」とあるが、
  実際にはどのフォルダにも付いていない。既存の運用に合わせて付けないままでよいが、
  新規作成時に迷ったらユーザーに確認する。

### ファイル名の月 = 対象月 とは限らないカード

| カード | 命名 | 意味 |
|---|---|---|
| 楽天カード | `enavi202605(下4桁).csv` | **請求月**。5月請求＝4月利用分。4-6月利用分は 202605/202606/202607 になる |
| PayPayカード | `detail202604(下4桁).csv` | 利用月そのまま |
| AMEX系 | `2026-04ANA AMEX TAKUYA.pdf` | 利用月そのまま |
| AMAZONマスター | `202604AMAZON TAKUYA.numbers` | 利用月そのまま |

楽天カードは1ヶ月ずれるので、月次の抜けを機械判定するときに誤検出しやすい。
`compare_quarters.py` にはこのオフセットを渡せるようになっている。

## 03.PayPay履歴 の口座

1-3月分では **16口座** を提出している（TAKUYA 12 / KAORI 2 / その他名義 2）。
ファイル名は口座番号の下4桁〜全桁でばらついていて、同じ口座でも表記が揃っていない。

**実際の口座番号一覧はここには書かない。** 正は提出状況報告シートの口座一覧。
突き合わせるときはシートを開いて確認する（シートの読み方は `browser-techniques.md`）。

同じ口座のCSVを2回DLすると重複提出になる（1-3月分でKAORIの1口座に「のコピー」が発生）。
**1口座1ファイル**を守る。監査では下4桁でマッチングして重複を検出する。

## 04.楽天ポイント履歴 の構造差

- 1-3月分: `楽天ポイント履歴　TAKUYA` / `楽天ポイント履歴　KAORI` のサブフォルダに分けている
- 4-6月分: ファイルを直置き

中身が揃っていれば実害は薄いが、揃えるならサブフォルダ方式に合わせる。
